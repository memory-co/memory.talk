## 1. 一句话:task 是「把一件事做下去」的载体,复杂的事就是一棵 task 树

一个 task 对应**一件要做成的事**。这件事可以很小——修一个 bug;也可以很大——把某个功能从设计做到上线。大事是由小事组成的,所以 **task 可以有子 task,一件复杂的事就是一棵 task 树**:根是「把 X 做出来」,往下拆成几步,每一步再拆,叶子是真正坐下来干的那一件小事。

在树的任何一层,task 都做同一件事:**把为了这件事用到的现场收拢到一起**——一个跑 Claude Code 的会话、一个跑 Codex 的会话、一个裸终端、几个正在看的网页、一个文件目录。从哪开始、中途用了什么、做到哪了、最后怎么样,都在这里。

它是 v5 的**顶层入口**:打开 memory.talk 看到的是 task 树,而不是 session 列表。session 退到 task 里面,成为 task 的成员。

---

## 2. 为什么是树:task 承载「定下来、正在做」的事,issue 承载「还没定」的事

v5 三层里只有 task 有**状态和完成**。issue 是 IBIS,故意不关闭、不拍板(见 [issue.md §5](issue.md));card 是词条,只有内容和历史、没有进度。但做事必须能说「这步完了」,所以**执行的结构——拆分、顺序、状态、完成——全部落在 task 上**,不落在 issue 上:

- **拆分 = 子 task**。一件事怎么拆,拆出来的每一块就是一个子 task。
- **状态 = 每个 task 自己的**:待做、在做、做完(或放弃)。父 task 的进度就是看子 task 的状态。
- **完成 = 叶子做完,往上收拢**。叶子 task 做完冻结;父 task 等它所有该做的子 task 都完了,自己才算完。根 task 可以活很久。

而「怎么拆」「选哪条路」这类**还没定**的事,不在 task 里硬写,而是提成一个 issue,由树上对应的 task 来管(§6);issue 里某个立场站住了,那个立场就变成树上的一个新节点——**一个决定,就是一个 issue 的胜出立场被转成了 task 树上的节点**(或者写成一张 card)。这就是 task 和 issue 的分工:task 装已定的,issue 装未定的。

树不深也不严格:一件小事就是一个孤零零的叶子,不必先建根;一棵树也不要求每层都整齐。层级只是「这件事属于哪件更大的事」这一条关系,别的不附加。

## 3. 跟 shellbase window 的关系:底层逻辑完全一致,在 memory.talk 里原生实现

**shellbase 到此为止,不再作为独立项目存在;它的 window 在 memory.talk 里原生实现,就是 task 的画布。** task 不另起一套运行时——shellbase 的画布、块、块即 URI、终端 attach、无中生有 + 重入、后端是状态唯一权威,这套底层逻辑 task **完全一致地**实现一遍,只是搬进 memory.talk 自己的进程和存储里。打开一个 task,就是打开它的画布;在 task 里开一个 Codex 会话,就是在画布上放一个 `codex://` 块。

**树上任何一层的 task 都可以有自己的画布**——你现在在哪一层干活,就打开哪一层。通常画布在叶子上(那是真正坐下来干的地方),但根 task 也可以有一块画布,用来开总览、议事、派活。

但画布和 task **重心**不一样:

| | window(画布) | task |
|---|---|---|
| 关心什么 | 屏幕怎么分、每块多大、放在哪 | 有哪些现场、它们是为了什么事汇在一起、事做到哪了 |
| 布局 | 是它的核心状态,精确持久化 | **只是一个视图**,可以随时重排、重排不影响 task 本身 |
| 成员身份 | 由 URI 里的 `window` + `block` 位置参数决定 | 由「它属于这个 task」决定,跟摆在画布哪里无关 |
| 生命周期 | 页面开着就在 | 有目标、有状态、有开始、有做完,还有父子 |

所以:**画布是 task 的显示层,task 是画布的意义层**。布局丢了、重排了、换个设备打开分割方式全不一样——task 一点没变,因为 task 记的是**成员、目的和进度**,不是网格坐标。

> 这条决定了原生实现时**唯一有意偏离 shellbase 的地方**:shellbase 里终端身份挂在 `block` 序号上,序号又跟布局绑着;task 里的成员身份要**脱离布局**——一个会话是这个 task 的成员,不因为它被移到别的格子就变成另一个会话。其余底层逻辑照搬,只有身份这一点在 URI 模型上要改,细节另篇。

## 4. task 里装什么:各种「现场」,不只是 agent 会话

task 的成员是**现场**(一个活着的、可以回去看的东西),不限于 code agent:

| 成员类型 | 例子 | 它对 task 的意义 |
|---|---|---|
| **agent 会话** | `claude:///proj`、`codex:///proj` | 干活的主力;它们的 round 是 task 留下的主要痕迹 |
| **终端** | `bash:///proj` | 人自己动手的地方;跑测试、看日志 |
| **浏览器窗口** | `https://…` 的文档、issue 页、dev server 预览 | 为了这件事**看过什么**——也是上下文的一部分 |
| **文件视图** | `file:///proj/src` | 事情落在哪个目录 |

关键是:**它们都是同一件事的一部分**。在画布上它们是并排的几个块;在 task 的意义上它们是「做这件事时打开过的所有东西」。一个 task 里可以同时跑多个 agent 会话(一个 Claude Code 写代码、一个 Codex 做 review),它们互相看得见对方的工作目录,也共享 task 的目的。

task 本身还有一点自己的东西,不多:**它是什么事**(一句话目标)、**在哪个项目**(工作目录)、**属于哪件更大的事**(父 task)、**做到哪了**(状态)、**什么时候开的、什么时候算完**。task 不做认知,不打分,不抽卡——那是 issue 和 card 的事。

## 5. session 怎么成为 task 的成员:在 task 里打开,就是它的

这是 task 相对 v3 / v4 最实在的一个改变。以前 memory.talk 认 session 归属靠**事后推断**:sync 从平台目录把会话抄进来,再拿 `cwd` 这类物理信号猜它属于哪个 explore。v5 里不用猜——

- **在 task 里开一个 agent 块,这个会话从诞生那一刻就是 task 的成员。** memory.talk 拉起它、看着它跑、记它的 round,归属是原生的。
- 同一个项目目录,可以在不同 task 里各开各的会话,它们互不相干——归属看 task,不看目录。
- **一个会话只属于一个 task,而且是树上的一个确定节点**,不属于「整棵树」。要在别的事里用到它的结论,走 issue / card,不是把会话搬家。
- 从外部平台导入的历史会话(v3 的 sync 路径)继续保留,作为没有 task 归属的会话存在;要不要给它们补一个 task、怎么补,是兼容问题,后面再说。

## 6. task 的一生:开工 → 干活(拆、议、派)→ 做完 → 留下痕迹

粗线条地看,一个 task 就四段;树上每个节点都走这四段,只是根和叶子的重心不同:

1. **开工**:说清要做什么事、在哪个项目、属于哪件更大的事;memory.talk 拿这句目标去撞 card,把相关的认知先注入进来——这是 recall 在 v5 的落点:**recall 的对象是 task,不再是零散的会话**。
2. **干活**:往 task 里加现场,agent 跑、人看、网页翻。这段时间 task 就是一块画布,怎么排随便。事情大了就**拆**成子 task;碰到没定的事就**议**——提一个 issue,由这个 task 来管;议出「得去做 X 才知道」就**派**——为那条论证开一个 task(见 [issue.md §4](issue.md))。
3. **做完**:事成了(或者放弃了),task 结束。叶子结束以后成员冻结:会话不再追加 round,现场可以回去看,但不再是干活的地方。父 task 的「做完」由子 task 收拢而来。
4. **留下痕迹**:task 留下的是它所有成员的记录——agent 会话的 round、看过的网页、动过的目录;树留下的是这些痕迹加上**它是怎么拆的、每步怎么定的**。这堆痕迹是 **issue 层的原料**:逐 round 标注在这上面做,`#问题` 从这里冒出来。

第 4 段就是 v3 explore 想要的东西,在 task 里天然成立:**一个 task 的会话是它自己提出的问题的先验素材;后面的 task 是这些问题的后验证据**。不用再画一条时间分割线——task 的边界就是那条线。

---

## 7. task 跟 issue / card 怎么接

task 是三层里最「实」的一层,它跟另外两层有三个接口:

- **往上:task → issue**。task 的痕迹被逐 round 标注,标注里的问题建 / 挂到 issue。一个 issue 记得它是从哪个 task 的哪些 round 冒出来的;一个 task 也能反过来列出「这件事引出了哪些问题、对哪些老问题给了新论证」。
- **往回:issue → task**。每个 issue 由树上一个 task **管**(manager)——通常就是正卡在这个问题上的那个节点;issue 也可以为某条论证的取证**派出**一个新 task,派出去的 task 做完,结果落回 issue 当论证。派出的 task 挂在树上哪里,由派它的 manager 决定,通常就是 manager 的子节点。task 本身不因此变成另一种东西——它只是多知道一件事:「我是为哪个问题开的」。见 [issue.md §3–§4](issue.md)。
- **往下:card → task**。task 开工时,recall 把命中的 card 注入到 task 里的 agent 会话中。注入的是 card,不是 issue,也不是别的 task 的会话原文。

task 之间**只有父子这一种直接关系**。同一棵树之外的两个 task 有关系,是因为它们碰到了同一个 issue、被同一个 issue 派出、或者用了同一张 card——横向关系走认知层,不走任务层。这样 task 可以一直很简单:一个容器、一句目标、一堆现场、一个父亲、一个状态。

---

## 8. 这篇有意不定的事

- **结束的判定**:叶子由人手动点「做完」,还是长时间没动静自动归档;父 task 是子 task 全完就自动完,还是也要人确认。
- **agent 会话之外的成员留什么痕迹**:浏览器窗口的访问记录、终端里敲过的命令,要留到什么程度才够当 issue 的原料,又不至于把什么都往里塞。
- **一块画布能不能跨多个 task**:本篇按「一个 task 至多一块画布、一块画布只属于一个 task」写。如果实践中「我这个屏幕上同时在做兄弟节点的两件事」很常见,再考虑画布跨节点。
- **树的深度和形状要不要约束**:本篇不约束。若实践中出现「什么都往根下挂、树变成平的列表」或「拆得太碎」,再考虑。
- **成员身份脱离布局**怎么落到 URI 身份模型上(§3 末),这是原生实现时唯一有意偏离 shellbase 的地方,单独一篇。
